# [2026-08-29] Handoff 分配缺少可证明的确认、超时与重启隔离边界

- **现象 (Symptom)**：旧实验实现把 Scheduler reservation、Router 投递和 P/D 分配散落在异步路径中；迁移时无法证明 Prefill 在 Router 持久化目标前不会被派发，也无法证明 Prefill 完成前 Decode 不会被提前分配。调用超时、取消、交付确认响应丢失或 Scheduler 非优雅重启后，还可能遗留 reservation、workload 或 Router 账目并错误恢复接流。尤其是确认请求已在 Scheduler 成功但响应丢失时，Router 若直接按失败撤销，会把“所有权已转移”误判为“从未确认”。
- **根因 (Root cause)**：协议没有携带 `(request_id, attempt_seq, scheduler_epoch)` 的唯一 attempt 身份，也没有把 pending delivery、ownership transfer、Prefill settlement 和 Decode commit 建模为带类型化结果的显式状态转换；同时缺少严格的 client/server/stage 超时序、交付租约，以及 `RUNNING/DRAINING/STOPPED/RECOVERING` 生命周期。初版运行时接线还把 RPC 返回当作确认真值，没有在确认或撤销响应不确定时查询 Scheduler 的权威状态。
- **为什么会写出 (Why)**：把一次函数返回视为跨进程所有权已转移，忽略 Scheduler 成功、Router 持久化、确认响应及实际派发之间均可能独立失败；把 RPC 超时误当成业务已取消；把进程重启误当成可以恢复内存事务；同时把 P/D 统一预分配错误套用到 P-first、D-deferred 的 Handoff 时序。
- **修复 (Fix)**：`handoff_protocol.py` 由 Scheduler 协议服务持有 attempt、pending-delivery、Decode workload 和 terminal receipt，Router 账本确认后才能派发；Prefill 幂等释放后才允许 Decode commit，并在提交前重查 topology、circuit、role 和 engine type。运行时增加 `TARS_STATUS` 权威状态查询：确认响应丢失时仅在 Scheduler 报告 `confirmed` 后继续，撤销响应丢失时仅在终态收据可证明时删除 Router 账本，其他歧义保持账本并失败关闭。新增严格超时预算、交付租约/状态对账、原始取消传播、排空截止时间和 Scheduler epoch 冷隔离；Scheduler stop 先拒绝新的单角色/联合 admission，继续服务已有生命周期直至收敛或截止，最终 quiesce 补偿包括已确认在内的残留实际 workload；非优雅重启不宣称事务恢复。
- **测试拦截 (Test interception)**：`test_tars_handoff_protocol.py` 覆盖确认前派发拒绝、提前 Decode 拒绝、重复请求/确认/撤销/生命周期幂等和类型化失败；对 8 个协议边界各注入 100 次失败并验证瞬态账本归零，连续执行 1000 个 attempt 验证三方身份一致，并执行 10,000 次乱序超时/取消竞争、50 个非优雅重启切点、交付租约过期和排空截止测试。`test_tars_scheduler_client_activation.py` 另覆盖确认响应丢失后查到已确认、撤销响应丢失后查到终态，以及状态仍歧义时保留 Router 账本三个运行时边界；`test_tars_runtime_activation.py` 覆盖 drain 拒绝新联合 admission 和 quiesce 清理已确认 workload。
- **场景 (Scenario)**：Handoff P-first/D-deferred、Router 持久化或确认中断、调用方取消、交付租约到期、排空、Prefill 回调重试、Decode 目标熔断/拓扑更新/引擎不匹配、Scheduler epoch 切换和非优雅重启。
- **关键词 (Keywords)**：TARS、Handoff、delivery lease、status reconciliation、confirmation response loss

## 2026-11-12：按分配所有者释放 SHM workload

- **现象与根因**：master 已删除 `WorkloadLedgerMixin` / `Scheduler.update_workload_sync`，迁到 schema-4 SHM CAS；旧 TARS activation、policy 和 server handler 仍调用已删除接口，无法真实分配/补偿 workload。接线修复后，Router 仍会先发送 TARS terminal lifecycle，再执行通用 workload cleanup。若两条路径都扣减同一个 endpoint，会释放其他请求的 token；仅删除 active attempt 账本无法辨认后续 cleanup 的所有者。反过来，跳过全部 TARS 配置下的 CAS 会泄漏 Trigger D-first 和 admission fallback 的普通分配。
- **修复边界**：Client 接收交付时持久化 `(request_id, attempt_seq, role, instance_id, endpoint_id)` 的独立 server-owned receipt，含 epoch/token。通用释放通过 `TARS_RELEASE_WORKLOAD` 交给 Scheduler 根据实际 receipt 幂等结算，不接受 Router 提供的扣减量；普通 D/fallback 仍使用 worker CAS。Client 仅在明确的 `success: true` ACK 后记录已释放，保留 tombstone 到 Router drain 与 residual cleanup 完成；响应不确定或 drain 失败时保留身份。terminal lifecycle 不删除这些资源收据。`UpdateWorkloadParams.attempt_seq` 显式传递 attempt，不解析日志 operation_id。
- **本地记录失败**：Bootstrap 为 P/D 两侧记录实际 owner；任一侧本地记录失败或取消，先通知 abort，再对两侧按 attempt 释放。只在释放 ACK 后删除对应 RequestManager 记录，残留记录仍可被最终回收路径发现。
- **Scheduler 边界**：实际 workload 通过 SHM adapter 结算，收据保存分配时的 generation，拒绝在拓扑复用后的新 slot/generation 上补偿旧分配；清除旧 mixin/handler 接口。重复 prepare 必须匹配原始请求 fingerprint，已经交付的 attempt 不因后续证据不可用而再次降级/分配；改变输入的重放失败关闭。drain、终态释放与单资源释放共用实际 receipt，失败补偿保留待重试状态，成功结算保留有界幂等 tombstone。
- **有界停机**：原 `server.stop` 在原生结算永久失败时会无限等待 `drain_complete`。现按 `tars.drain_timeout_s` 到期停止任务，并进行一次 quiesce；若仍有 receipt，明确记录强制冷停/需要恢复的 error，然后关闭 SHM/socket，不把未完成补偿报告为成功。
- **回归测试**：`test_tars_scheduler_client_activation.py` 覆盖 terminal 后 cleanup、重复 cleanup、release 响应丢失、无效 ACK、请求身份复用、Bootstrap 双资源及普通 D/fallback CAS；`test_base_router_prepare_resource.py` 覆盖 rollback 的 attempt 传播，`test_unified_pd_router.py` 覆盖 Bootstrap 本地持久化异常与取消补偿。真实 dispatcher/SHM adapter 边界由 `test_tars_runtime_activation.py` 覆盖。
- **本轮验证**：通过仓库 `bash tests/run_tests.sh` 执行 runtime activation 与 SHM adapter 边界，共 51 项通过，覆盖 real client → dispatcher 的 terminal/lost-release-ACK、generation 隔离、重复 prepare/fingerprint、证据不可用、drain 中 await 及补偿重试。刷新 master 后的 Client/connection manager/cache lifecycle/Agent epoch channel 回归 114 项通过；11 项缺少原生 SHM 库跳过（8 个 CAS、3 个 cache-lifecycle E2E），另 1 项沿用既有 endpoint-status skip。原生共享内存与硬件部署仍需在目标 Linux 环境验证。
- **配置迁移**：TARS 要求 `prefill_scheduler_type` 与 `decode_scheduler_type` 同时启用，配置加载、Scheduler/Client 构造、connection manager 与 Router 共用判定。旧 `scheduler_type` 仍只填充未显式设置的角色字段，显式的两侧非 TARS 值不会创建 TARS 状态。部署校验与示例同步采用两侧字段。
- **Hybrid override 迁移**：master 的 Decode co-location `prepare_resource` override 也必须接受并转发新增的 `attempt_seq` / `coordination_mode`；否则基类资源上下文在普通 Hybrid 请求中同样会触发 `TypeError`。P/U 与 D-colocation 两侧均显式保留 attempt 身份，同时保留 D 的 capability gate。
- **可选 POSIX 能力**：`session_affinity_shared` 缺少 `fcntl` 时允许纯模型导入，但 shared table 在分配资源前抛出 `ImportError`，由既有入口回退到真实本地 affinity；不提供假锁。`test_session_affinity.py` 与 `test_scheduler_server_shutdown.py` 验证该边界以及 drain 中恢复、quiesce 恢复、永久失败的停机时限/清理/日志；连同 SHM adapter 的定向 runner 共 74 项通过。这不代表验证了 POSIX flock 或 Rust native 互操作。
- **Agent Hint 接线**：新 master 的 KVC lifecycle 根据 session pin 寻找管理目标，而 TARS 确认成功后提前返回，绕过普通 CAS 成功分支的位置/TTL 记录，导致 sender 报告 no-pin 并跳过管理。现在普通分配与 TARS P/U、Bootstrap P+D 共用 `_record_allocation_state`，只在确认成功后写入实际 instance/endpoint、请求的 Agent session epoch 及显式 TTL。`route=0` 仍记录位置，不能用 affinity 重选 TARS 目标；确认失败或取消不写记录。Agent session epoch 与 TARS scheduler epoch 分开；可选 hint 存储失败只记录 warning，不把已确认分配变成孤儿。Agent finalize 清理 session pin 不删除 workload receipt。
- **Agent Hint 验证**：`test_tars_agent_hint_integration.py` 的 18 项全部通过，覆盖确认后 P/U/joint 的精确位置/epoch/TTL、确认拒绝/取消、route=0、真实 KVC sender 到 HTTP 边界的目标选择、CentralLifecycle 先 evict 再 finalize 清 pin，并验证保留 TARS receipt、abort 后重复 release 不扣减新请求。测试对 transport/evidence/native/HTTP 使用边界 double，不代表真实 Rust 或跨进程 Obs 验证。既有 client 回归另验证 hint 记录异常不会丢失已确认资源所有权。
